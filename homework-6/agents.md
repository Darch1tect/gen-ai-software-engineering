# Agent Guidelines: Multi-Agent Banking Transaction Processing Pipeline

These are binding operating instructions for any AI coding agent (Claude Code, Copilot, Cursor, or
otherwise) working in this repository. They operationalize `specification.md` into concrete
day-to-day rules for this capstone. Where this file and `specification.md` conflict,
**`specification.md` wins** — raise the conflict rather than silently picking one.

## 0. What this repo is

This is homework 6 of the gen-ai-software-engineering course: a capstone that builds **four
meta-agents** (specification, code generation, testing, documentation) whose combined output is a
working transaction-processing pipeline (validator → fraud detector → compliance checker →
settlement processor) driven by `integrator.py`. Unlike homework-3, this is **not**
documentation-only — code, tests, hooks, and MCP servers are all in scope from the start.

## 1. Tech stack

- **Python**, targeting the project's own `.venv` (created with Homebrew's `python@3.12`, since
  `fastmcp` and the `mcp` SDK need Python ≥3.10 and the system Python here is 3.9).
- `pytest` + `pytest-cov` for tests and the coverage gate.
- `fastmcp` for the custom MCP server (`mcp/server.py`).
- No web framework, no database — the "shared state" is the `shared/` directory tree of JSON
  files, by design (see `specification.md` § Message protocol).

## 2. Domain rules (banking pipeline specific)

- **Money**: always `decimal.Decimal`, always paired with an ISO 4217 currency code. Amounts are
  strings on the wire (JSON) and in file storage — never a bare JSON number, never a `float`
  anywhere in the codebase, including tests.
- **IDs**: `transaction_id` values come from the input data (`TXN00N`) and are treated as opaque —
  never parsed for meaning, never assumed sequential. `message_id` values generated by the
  pipeline itself are UUID4 strings.
- **PII**: `source_account` / `destination_account` are sensitive. Never write a full account
  number to `shared/results/audit.log` or to stdout — always mask via
  `agents.messaging.mask_account` (last 4 characters only). Full account numbers may still live in
  the per-transaction result JSON in `shared/results/`, since that file is the compliance record,
  not a log stream — do not conflate the two.
- **Fraud/compliance thresholds are simplifications, not production rules**: the $10,000 fraud
  threshold and the "structuring" band are applied in-currency with no FX conversion, and the
  sanctioned-country list is a small illustrative constant. Do not present these as
  regulatory-grade logic in docs or comments — say plainly that they're capstone-scope
  approximations, per `specification.md` § Implementation Notes.
- **Rule values live in `rules.yaml`, never as hardcoded constants in agent modules.** If you find
  yourself adding a module-level threshold/denylist/weight to `fraud_detector.py` or
  `compliance_checker.py`, stop — it belongs in `rules.yaml` under `fraud.*`/`compliance.*`, read
  via `data["_rules"]` (or `agents.rule_engine.load_rules()` as a standalone fallback). This is
  the entire point of the Rule Engine agent: changing business behavior should never require a
  code change or a new test of the constant itself.

## 3. Code style & structure

- One responsibility per agent module in `agents/` — do not merge validator/fraud/compliance/
  settlement logic into one file for convenience, even though they're small. Each agent module
  exposes exactly one pure(ish) function taking a transaction dict and returning a result dict; it
  does not itself decide pipeline ordering — that's `integrator.py`'s job.
- `agents/messaging.py` is the only place that touches `shared/` paths, timestamps, masking, and
  the audit log directly. Individual agent modules call into it rather than reimplementing file
  I/O.
- Every low-level task in `specification.md` maps 1:1 to a file/function pair — if you add a new
  agent or helper that isn't in `specification.md` § Low-Level Tasks, update the spec (and re-run
  `/write-spec` if convenient) rather than letting them drift apart.

## 4. Testing & verification expectations

- Every agent module gets its own `tests/test_<agent>.py` covering at least one pass path and one
  reject/flag path. `tests/test_integration_pipeline.py` runs `integrator.run_pipeline` end-to-end
  against a `tmp_path`-isolated copy of `shared/` — tests must never write into the real
  `shared/` directory used for manual runs.
- Coverage gate is **80%**, enforced by `.claude/hooks/check_coverage.sh` on `git push` attempts.
  Aim for ≥90% (per `specification.md` § Ending context) — don't treat 80% as the target, treat it
  as the floor.
- Never claim a mid-level objective from `specification.md` is met without a test that actually
  exercises it (e.g. the >10,000 fraud flag, the `XYZ` currency rejection, the structuring band).

## 5. Security & compliance constraints

- **Never** log a full account number or customer name, in any environment, including debug
  output — this applies to `shared/results/audit.log` and to anything printed by `integrator.py`
  or the MCP server.
- **Always** write an audit-log line for every agent decision on every transaction, including
  rejections — a transaction that "obviously" got rejected still needs an audit trail entry.
- **Always** treat `shared/results/` as append/write-once per run — `integrator.py` clears and
  rebuilds `shared/{input,processing,output}` on each run, but `shared/results/` output should be
  reproducible from a given `sample-transactions.json`, not silently merged with a stale prior
  run's leftover files.

## 6. How to treat ambiguity

- If `sample-transactions.json` contains a case the spec doesn't obviously cover (it does — see
  the `XYZ` currency, the negative refund amount, and the near-threshold amount), treat it as an
  intentional test fixture, not a data error — the pipeline must produce a deliberate,
  spec-consistent decision for it, not crash or silently skip it.
- Do not guess at a genuinely ambiguous requirement and proceed silently. If `specification.md`
  doesn't say, that's a spec gap — say so and propose an update rather than picking an
  interpretation and moving on.

## 7. Prohibited actions

- Do not run a real `git push` to `origin` as part of demonstrating the coverage-gate hook — use a
  synthetic hook payload instead (see `specification.md` and `HOWTORUN.md`).
- Do not weaken the 80% coverage gate to make a push easier — if coverage is genuinely short, write
  more tests, don't lower the threshold in `check_coverage.sh`.
- Do not use `git push --force`, skip test suites, or bypass hooks (`--no-verify`) without explicit
  human authorization.
